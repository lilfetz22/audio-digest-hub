#### [CRITICAL] `savePlaybackPosition` writes the *new* part's position onto the *previous* part's row

- **Location:** lines 108–124 (`savePlaybackPosition`), 217–231 (`handlePause` / `handleEnded`),
  373–377 (5 s interval), 381–390 (visibility flush); interacts with `src/pages/Player.tsx`
  lines 65–84 and 123–184.
- **Issue:** `savePlaybackPosition` pairs `audiobookRef.current.id` with `audio.currentTime`,
  but after an auto-advance those two belong to **different parts**. `handleEnded` swaps
  `audio.src` to part 2 synchronously and *then* calls `navigate()`; `audiobookRef.current` is
  only updated after the `/player/:nextId` fetch (`supabase.select` + sign) resolves. Every
  save that fires inside that window attributes part 2's timeline to part 1's row.

  Concrete failure (the exact scenario this branch targets — screen locked, unattended):
  1. Part 1 ends. `pause` → save `floor(duration)` to part 1 (correct). `ended` → save
     `floor(duration)` to part 1 (correct). `loadSource(url2, { autoPlay: true })` swaps the
     source; the `play` event sets `isPlaying = true`, so the 5 s interval restarts with
     `audiobookRef.current === part1`.
  2. The phone is locked, so the part-2 `select` is throttled and does not resolve for tens of
     seconds (or until the screen wakes). `audiobookRef.current` stays part 1.
  3. The interval fires at t+5 s and runs
     `update({ last_playback_position_seconds: 5 }).eq('id', part1.id)`, and keeps doing so
     every 5 s. A `visibilitychange` (user unlocking the phone) does the same thing
     immediately.
  4. Result: part 1's row is now ~5 s instead of complete. `src/pages/Dashboard.tsx:145-155`
     renders that as a progress bar, so a finished part reads "2 %"; reopening part 1 resumes
     5 s in, and the end-of-part resume guard (line 198) no longer triggers because the saved
     value is no longer near the end. Part 2's own row is never written during the window, so
     if the app is killed mid-part-2 that progress is lost too.

  Shorter, higher-probability variant: the user hears part 2 start and taps pause within the
  fetch window — `handlePause` (line 220) writes part 2's 2 s onto part 1's row.
- **Suggestion:** make the row that owns the loaded media explicit and refuse to save when it
  disagrees with `audiobookRef.current`.

#### [WARNING] `isPlaying` stays `true` after a source swap that does not auto-play

- **Location:** lines 156–168 (`loadSource`, new-URL path)
- **Issue:** the media load algorithm sets `paused = true` **without firing a `pause` event**
  (HTML spec §4.8.12.5 step 6.6 — Blink and WebKit both only reject pending play promises
  there). So when `loadSource` assigns a new `src` with `autoPlay: false`, the element goes
  silent but no listener updates `isPlaying`, and nothing reads the flag back off the element
  any more now that `syncAudioState()` is gone.

  Reachable path: auto-advance to part 2 (playing), then press the browser **Back** button.
  `id` becomes part 1 and `location.state.autoPlay` for that history entry is `undefined`
  (the user originally arrived from the dashboard), so the load effect calls
  `loadSource(url1, { autoPlay: false, startAt: pos1 })`. Audio stops, but
  `PlayerControls` still renders the **Pause** icon (`PlayerControls.tsx:112`). Tapping the
  pause-looking button calls `togglePlayPause`, sees `audio.paused === true`, and *starts*
  playback — the opposite of what the icon promised.
- **Suggestion:**
  ```ts
      audio.src = url;
      applyPlaybackRate(audio, rateRef.current);
      audio.load();

      if (options.autoPlay) {
        startPlayback();
      } else {
        // The load algorithm pauses the element without firing `pause`, so the
        // UI would otherwise keep showing a Pause button over silence.
        setIsPlaying(false);
      }
  ```

#### [WARNING] The unmount `flush()` in the visibility effect is a no-op, so leaving the player drops the last seconds of progress

- **Location:** lines 381–390 (flush effect), 108–111 (`savePlaybackPosition` guard)
- **Issue:** the cleanup's `flush()` only runs on unmount (deps are the stable
  `savePlaybackPosition`). React detaches host refs during the **mutation** phase of a
  deletion, while passive-effect destroys for a deleted subtree run later in the passive
  phase. By the time `flush()` executes, `attachAudio(null)` has already set
  `audioRef.current = null`, so `savePlaybackPosition` returns at the `if (!book || !audio)`
  guard and writes nothing.

  Failure scenario: user listens for 8 s past the last 5 s checkpoint, taps "Back to Library".
  The `<audio>` node is removed (its own `pause` event arrives in a later task, after the
  listeners were removed), the unmount flush no-ops, and the DB keeps the stale checkpoint —
  up to 5 s of progress silently lost on every exit. The comment above the effect claims the
  opposite, so the bug is invisible to the next reader.
- **Suggestion:** keep the last known position in a ref so saving does not depend on the
  element still being attached (this also composes with the CRITICAL fix above):
  ```ts
  const lastPositionRef = useRef(0);

  // handleTimeUpdate (line 179)
  const handleTimeUpdate = () => {
    lastPositionRef.current = audio.currentTime;
    if (!isSeekingRef.current) setCurrentTime(audio.currentTime);
  };
  // handleSeeked (line 251) and loadSource both keep it in sync:
  //   handleSeeked  -> lastPositionRef.current = audio.currentTime;
  //   loadSource    -> lastPositionRef.current = options.startAt ?? 0;

  const savePlaybackPosition = useCallback(async (positionOverride?: number) => {
    const book = audiobookRef.current;
    if (!book) return;
    if (loadedBookIdRef.current !== null && loadedBookIdRef.current !== book.id) return;

    const position = Math.floor(
      positionOverride ?? audioRef.current?.currentTime ?? lastPositionRef.current,
    );
    if (!Number.isFinite(position) || position <= 0) return;
    /* ...unchanged update... */
  }, []);
  ```
  (Note: on a real page unload `pagehide` still cannot guarantee the `fetch` completes;
  `visibilitychange` is the reliable path and already covers backgrounding.)

### src/components/player/signedUrlCache.ts

#### [WARNING] A cached URL can be handed out with as little as 5 minutes of validity, and re-signing mid-transition defeats the `appliedSrcRef` guard

- **Location:** lines 3–5 (`TTL_SECONDS`, `REFRESH_MARGIN_MS`), line 26 (freshness test)
- **Issue:** the freshness test only guarantees `REFRESH_MARGIN_MS` (5 min) of remaining
  validity, but a part is 30–70 minutes long. Two distinct failures:

  1. **Expiry mid-part.** Part 2's URL is signed when part 1 *loads* (the pre-sign effect,
     `Player.tsx:208-248`). If part 1 runs for 40 minutes of wall clock, part 2 starts on a
     signature with ~20 minutes left. Safari issues range requests for the whole 35 MB file,
     so once the token expires Storage answers 400/403 → the `error` event fires →
     `PlayerControls` disables every control (`disabled={!!error}`) and playback is dead
     until the user navigates away and back.
  2. **URL identity change during a transition.** If part 1 ran longer than
     `TTL - margin` (55 min), the cache entry is stale at transition time, so the part-2
     fetch in `Player.tsx:154` returns a *different* signed string than the one
     `goToNextPart` already assigned. `appliedSrcRef.current !== url` then, so the load
     effect re-assigns `audio.src` — which stops the part 2 that is already playing and
     calls `play()` from a React effect with no user activation. That is precisely the
     `NotAllowedError` this branch exists to eliminate.
- **Suggestion:** make the stable window longer than any listening session and the guaranteed
  validity longer than any part:
  ```ts
  /** Long enough that one path yields a byte-identical URL for a whole session. */
  const TTL_SECONDS = 12 * 60 * 60;
  /** Re-sign this far ahead so no part is ever started on a nearly-expired signature. */
  const REFRESH_MARGIN_MS = 2 * 60 * 60 * 1000;
  ```

#### [SUGGESTION] The cache outlives the session and is never bounded

- **Location:** lines 12–13
- **Issue:** `cache` is module state that survives sign-out. `audiobooks` rows and the
  `audiobooks` bucket are both RLS-scoped per user (`supabase/migrations`: storage policy
  `auth.uid()::text = (storage.foldername(name))[1]`), so a signed URL is a per-user bearer
  capability that stays usable for the full TTL after the user signs out on a shared device.
  Nothing in the UI can reach it (the metadata `select` is blocked by RLS first), so this is
  hygiene rather than an exploitable hole — but there is no reason to keep it, and the map
  also grows unbounded across a long session.
- **Suggestion:**
  ```ts
  export function clearSignedAudioUrlCache() {
    cache.clear();
    inflight.clear();
  }

  supabase.auth.onAuthStateChange((event) => {
    if (event === 'SIGNED_OUT' || event === 'USER_UPDATED') clearSignedAudioUrlCache();
  });
  ```

### src/pages/Player.tsx

#### [SUGGESTION] `goToNextPart` closes over a `loadSource` binding declared after it

- **Location:** lines 65–84 (note the `react-hooks/exhaustive-deps` suppression at line 82)
- **Issue:** the reasoning in the comment is correct **today**, but only because
  `loadSource` happens to be referentially stable (`useCallback([applyPlaybackRate])`, and
  `applyPlaybackRate` is `useCallback([])`). There is no TDZ hazard — the closure body only
  runs from event handlers, long after the binding is initialised — but the memoised
  `goToNextPart` permanently captures the *first* render's binding. The day someone adds a
  reactive dependency to `loadSource`, this call site silently keeps invoking the original
  one, with no lint signal because the rule is suppressed.
- **Suggestion:** indirect through a ref so the suppression and the assumption both go away:
  ```ts
  const loadSourceRef = useRef<((url: string, options?: LoadSourceOptions) => void) | null>(null);

  const goToNextPart = useCallback(
    (options: { autoPlay: boolean }) => {
      const next = nextPartRef.current;
      if (!next) return;
      loadSourceRef.current?.(next.url, {
        autoPlay: options.autoPlay,
        startAt: 0,
        ownerId: next.id,
      });
      navigate(`/player/${next.id}`, { state: { autoPlay: options.autoPlay } });
    },
    [navigate],
  );

  const { attachAudio, loadSource, /* ... */ } = useAudioPlayer(/* ... */);
  loadSourceRef.current = loadSource; // stable identity; assignment is idempotent
  ```

### src/pages/DevPlayerTest.tsx

#### [SUGGESTION] The inline `<audio>` ref callback makes the fixed harness re-render in a loop

- **Location:** lines 322–331 (and lines 186–192 in the legacy harness)
- **Issue:** the ref is a new function each render, so React detaches and re-attaches it on
  every commit: `attachAudio(null)` → `setAudioEl(null)`, then `attachAudio(el)` →
  `setAudioEl(el)`. Two queued updates force another render, which produces another new ref
  function, which forces another detach/attach — a self-sustaining render loop. `Player.tsx`
  avoids this by passing the stable `attachAudio` directly (`ref={attachAudio}`). Dev-only, but
  a spin loop distorts exactly the battery/timing behaviour the harness is meant to observe.
  Secondary: the harness feeds fake ids (`part-1`) into the real hook, so
  `savePlaybackPosition` fires `update(...).eq('id','part-1')` against the live Supabase
  project every 5 s and logs an invalid-uuid error each time.
- **Suggestion:**
  ```tsx
  const attachAndCount = useCallback(
    (el: HTMLAudioElement | null) => {
      attachAudio(el);
      if (el && !seen.current.has(el)) {
        seen.current.add(el);
        setElements(seen.current.size);
      }
    },
    [attachAudio],
  );
  // ...
  <audio ref={attachAndCount} preload="auto" />
  ```
  and give the harness parts UUID-shaped ids (or a `null` audiobook) so it stops issuing
  writes against the real table.

## Verified, no action

Points raised for independent confirmation that came out clean:

- **`loadSource` / `appliedSrcRef` double-load race.** Safe *as long as the URL string is
  stable*, which is the cache's job — so the only double-load path is the identity change
  covered by the signed-URL WARNING above.
- **Event ordering across the swap.** Correct. End of media fires `timeupdate` → `pause` →
  `ended` in one task (both saves attribute the finished position to the outgoing part, which
  is right). `audio.src = …` / `load()` set `paused = true` *without* a `pause` event and
  reject only *pending* play promises — `play()` is called afterwards, so nothing aborts it —
  and the subsequent `play` event leaves `isPlaying === true`. The redundant `audio.load()`
  after assigning `src` re-enters the load algorithm before resource selection has started,
  so it costs an extra `emptied`/`loadstart` but no extra network request; left alone since
  the path was device-validated.
- **`syncAudioState()` removal.** No state is left unsynced: `volume` and `playbackRate` are
  now state-driven via effects (lines 297–308), `duration` comes from
  `durationchange`/`loadedmetadata`, `currentTime` from `timeupdate`/`seeked`, and the only
  `isPlaying` gap is the non-autoplay swap filed as a WARNING above.
- **`user` → `user?.id`.** Correct fix: `useAuth` calls `setUser(session?.user ?? null)` on
  every `onAuthStateChange` emission, producing a new object identity on token refresh, so the
  old `[id, user]` dependency genuinely re-ran the fetch and reset state on refocus.
- **`playbackRate` persistence.** Setting `defaultPlaybackRate` alongside `playbackRate` is
  the right mechanism, `readStoredPlaybackRate` guards `parseFloat`/quota exceptions, and
  the persisted default (2) matches an option in the `PlayerControls` select.
- **Dev-only route does not leak.** `dist/assets/index-*.js` from `npm run build` contains no
  `devtest` / `Autoplay was blocked` / harness strings — Vite replaces `import.meta.env.DEV`
  with `false` and Rollup shakes the pure `_jsx` call, so `DevPlayerTest` is fully absent from
  the production bundle. React Router also ignores the resulting `false` child
  (`createRoutesFromChildren` skips non-elements), so there is no runtime error.
- **`scripts/gen-devtest-audio.mjs`.** WAV header fields, byte rate, block align, buffer
  sizing, beep-slot arithmetic and fade envelopes all check out; amplitudes cannot clip;
  invalid CLI durations exit non-zero. `public/devtest-part1.wav` confirmed ignored by
  `.gitignore:35`.
