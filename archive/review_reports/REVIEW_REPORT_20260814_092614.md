### pipeline.py

#### [WARNING] Module docstring describes a fallback path that an API failure never takes
- **Location:** lines 21-22 ("If step 3 can't reach the API, the range is omitted and each stage falls back to its own default rather than the run being skipped.")
- **Issue:** That is not what happens. When `/audiobooks` is unreachable,
  `find_last_upload_date` returns `None`, `resolve_default_dates` returns
  `[end_date]`, and `date_range.py` prints `2026-08-13 2026-08-13` and exits
  **0**. `resolve_date_range` therefore returns a real range, and
  `pipeline.py` pins `--start-date 2026-08-13 --end-date 2026-08-13` onto all
  three stages. Concrete scenario: the server was down for 08-11..08-13, the
  watermark is 08-10, and the Supabase project is cold so the first GET times
  out — the run silently processes only 08-13 and the days this branch exists to
  recover are skipped, with a docstring telling the next maintainer that the
  stages fell back to their own defaults (which would have re-tried the API and
  backfilled). The `None` path is only reached on a config-read failure,
  unparseable stdout, or a crash. `CLAUDE.md`'s table is accurate ("non-zero
  exit"); only this docstring is wrong.
- **Suggestion:**
  ```python
  # Step 3 decides which days everything else processes — normally "every day
  # since the last audiobook upload, through yesterday" — and steps 4-6 are all
  # handed that same window as --start-date/--end-date. Resolving it once is what
  # keeps the stages in agreement: they used to each work it out for themselves,
  # and disagreed, so a missed day produced an audiobook with no research digest
  # folded into it. If step 3 exits non-zero (config unreadable, unexpected
  # output), the range is omitted and each stage falls back to its own default
  # rather than the run being skipped. Note that an *unreachable API* is not
  # that case: date_range.py degrades to a yesterday-only range and exits 0, so
  # the backfill collapses to one day for that run and recovers on the next.
  ```

#### [WARNING] Unvalidated stdout tokens are passed straight into a `fatal=True` stage
- **Location:** lines 169-179 (`parts = result.stdout.split()`)
- **Issue:** Any two whitespace-separated tokens on stdout are accepted as
  dates. `resolve_date_range`'s whole purpose is to return `None` on garbage so
  the pipeline degrades gracefully, but it only does that for 1 or 3+ tokens.
  Concrete failure: if anything in the `date_range.py` subprocess ever writes a
  two-word line to stdout (a `print` added to `http_utils`/`date_range`, a
  wrapper/shim notice, a launcher message), `date_args` becomes
  `["--start-date", "Deprecation", "--end-date", "warning:"]`;
  `run_research_pipeline.py` then raises `ValueError` out of
  `datetime.strptime`, exits non-zero, and `run_step(..., fatal=True)` raises
  `SystemExit` — the audiobook is never generated. A soft failure is escalated
  into a hard pipeline abort at exactly the point the code is trying to be
  defensive. `pipeline_test.py` pins `"a b c"` → `None` but never `"a b"`, so
  the gap is untested.
- **Suggestion:**
  ```python
  import re
  _DATE_RE = re.compile(r"^\d{4}-\d{2}-\d{2}$")
  ...
      parts = result.stdout.split()
      if not parts:
          return ("", "")
      if len(parts) != 2 or not all(_DATE_RE.match(p) for p in parts):
          logger.warning(
              "Unexpected output from date_range.py (%r); each stage will fall "
              "back to its own default.",
              result.stdout,
          )
          return None
      return (parts[0], parts[1])
  ```
  and add `_completed(stdout="a b")` to the `returns_none_when_undeterminable`
  parametrize list in `pipeline_test.py`.

  ```python
          "wiki-ingestion",

          REPO_ROOT,
          fatal=False,
      )
  ```

  `generate-audiobook` are skipped.

#### [SUGGESTION] "API unreachable" and "no audiobooks yet" are indistinguishable to the CLI

  "I could not determine this — use your fallback". Behavior is self-healing (the

- **Suggestion:** thread a `strict` flag so only the CLI opts in, keeping the
  `date_range.find_last_upload_date` patch seam that
  `generate_audiobook_test.py` relies on:

  ```python
  def resolve_default_dates(api_url, api_key, end_date,

      if last_upload_date is None:
          if strict:
              raise WatermarkUnavailable(
                  "Could not determine the last upload date from the audiobooks API."
              )
          ...
  ```
  ```python
  # in main()
      try:
          dates = resolve_default_dates(
              api_url, api_key, yesterday,
              max_backfill_days=args.max_backfill_days, strict=True,
          )
  ```

#### [SUGGESTION] Negative `--max-backfill-days` silently means "unlimited"
- **Location:** lines 137 and 180-184 (`if max_backfill_days > 0`), plus the
  three CLI definitions (`date_range.py:240`, `generate_audiobook.py:726`,
  `run_research_pipeline.py:165`, `run_wiki_ingestion.py:70`)
- **Issue:** Only `0` is documented as "disable the cap", but every negative
  value takes the same branch. `--max-backfill-days -1` — a plausible way to
  express "no limit", or a typo — silently uncaps the backfill, so a deployment
  dormant since January wakes up and hands `generate_audiobook.py` 200+ days of
  Kokoro TTS in one `fatal=True` step, past the point where `seen_papers.csv`
  has dedup state.
- **Suggestion:**
  ```python
  # in date_range.resolve_default_dates / resolve_transcript_dates

  ```
  or, per CLI: `if args.max_backfill_days < 0: parser.error("--max-backfill-days must be >= 0 (0 disables the cap)")`
