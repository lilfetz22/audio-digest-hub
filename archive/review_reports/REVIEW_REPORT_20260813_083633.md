### src/audiobooks/research_papers/gemini_client.py

#### [CRITICAL] Negative `Retry-After` reaches `time.sleep()` and raises `ValueError`
- **Location:** line 47 (`return float(int(value))`), consumed at line 369 / 386
- **Issue:** The HTTP-date branch clamps to `max(..., 0.0)`, but the delta-seconds branch does not. A response header of `Retry-After: -1` (or `-30`, which some proxies and misbehaving gateways emit alongside a 429/503) parses to `-1.0`. That is not `None`, so the `retry_after is not None` branch is taken; `delay > max_delay` is false so no clamp applies; `time.sleep(-1.0)` then raises `ValueError: sleep length must be non-negative`. `ValueError` is not in the `except (httpx.ReadError, ..., OSError)` tuple, so it escapes `_try_openrouter` → `generate()` → the caller. In `openrouter_only` mode (the wiki engine's default configuration) and in the transcript generator this aborts the run on a header the server controls — untrusted input crashing the client.
- **Failure scenario:** OpenRouter returns `429` with `Retry-After: -1` on attempt 1 of 4 → pipeline dies with an unhandled `ValueError` instead of backing off.
- **Suggestion:**
  ```python
  def _parse_retry_after(value: str) -> float | None:
      if not value or not value.strip():
          return None
      value = value.strip()
      try:
          return max(float(int(value)), 0.0)   # clamp: servers may send negatives
      except ValueError:
          pass
      ...
  ```
  Optionally also assert the invariant at the call site: `delay = min(max(retry_after, 0.0), max_delay)`.

#### [WARNING] Waiting threads issue their LLM request while holding `_resolve_lock`, serializing the whole thread pool
- **Location:** lines 133–141 (`with self._resolve_lock:` → `_try_resolved(...)`)
- **Issue:** Inside the lock the code re-checks `self._resolved` and, if set, calls `_try_resolved`, which performs the full network request (and up to 3 back-off sleeps) *while still holding the lock*. So once any single call misses the fast path, every other queued caller executes its request one-at-a-time under the lock. With `WikiIngestionEngine(max_workers=4)` this is the common case: 4 threads start simultaneously, `self._resolved` is `None` for all of them, one walks the chain and the other three then run their entire generation serially under the lock. The advertised parallel section analysis degrades to sequential for the first (and every subsequent post-failure) batch. This is compounded by `_walk_tier_chain` itself holding the lock across the entire retry ladder — 2 keys × 2 models × (5+10+20 s) plus a 4-attempt OpenRouter fallback with 120 s timeouts, i.e. several minutes of total stall for every other thread.
- **Suggestion:** Use the lock only to publish/read the resolved pair, and release it before doing I/O:
  ```python
  with self._resolve_lock:
      resolved = self._resolved
      if resolved is None:
          return self._walk_tier_chain(system_prompt, user_prompt, response_format)
  # lock released — every waiter now runs its own request concurrently
  result = self._try_resolved(resolved, system_prompt, user_prompt)
  if result is not None:
      return result
  with self._resolve_lock:
      resolved = self._resolved
      if resolved is not None:
          result = self._try_resolved(resolved, system_prompt, user_prompt)
          if result is not None:
              return result
      return self._walk_tier_chain(system_prompt, user_prompt, response_format)
  ```
  (`_resolve_lock` is already an `RLock`, so `_invalidate_resolved` re-entry stays safe.)

#### [WARNING] `None` is overloaded as the "locked-in pair failed" sentinel, but `_try_model` can legitimately return `None`
- **Location:** line 289 (`return response.text`), lines 128–141, 145–170
- **Issue:** `_try_model` is annotated `-> str` but returns `response.text`, which the `google-genai` SDK sets to `None` when a candidate has no text part (safety block, `MAX_TOKENS` with no content, tool-only response). `_try_resolved` returns `None` to mean "that pair failed, re-enter the chain", so a legitimate empty completion is misread as an infrastructure failure: the locked-in pair is invalidated, the entire tier chain is re-walked (burning quota on primary *and* backup keys), and if the chain succeeds it locks in a pair that returns `None` again — `generate()` then returns `None` from a `-> str` function. Downstream, `parse_json_response` tolerates `None`, but `transcript_generator` string operations do not.
- **Failure scenario:** One safety-filtered paper abstract → every subsequent `generate()` call re-runs the full 4-tier chain, and the caller receives `None` instead of a string or an exception.
- **Suggestion:** Make the empty case explicit rather than sentinel-encoded:
  ```python
  response = client.models.generate_content(...)
  text = response.text
  if not text:
      raise RuntimeError(f"{model} returned no text (finish_reason may be SAFETY/MAX_TOKENS)")
  return text
  ```
  and let `_try_resolved`'s existing `except` clauses (or a new `except RuntimeError`) decide whether re-entering the chain is warranted — an empty completion is a prompt problem, not a tier problem, so it should probably propagate.

#### [WARNING] Back-off has no jitter; parallel workers retry in lockstep
- **Location:** lines 274–276, 300, 317, 336–338, 375, 421
- **Issue:** `delay = min(base_delay * (2 ** attempt), max_delay)` is fully deterministic. The new `max_workers=4` thread pool means four calls fail against the same rate-limited endpoint at nearly the same instant, sleep exactly 5 s, then all four retry simultaneously, get 429 again, sleep exactly 10 s, and so on — a synchronised thundering herd that re-triggers the very limit it is backing off from. The retry budget was also cut from 10 attempts / 30 s base / 600 s cap to 4 / 5 s / 60 s, so total back-off per model drops from many minutes to 35 s, right as concurrency quadruples. The two changes compound.
- **Suggestion:** Add full jitter to every back-off computation:
  ```python
  import random
  delay = min(base_delay * (2 ** attempt), max_delay)
  delay = random.uniform(delay / 2, delay)  # decorrelate concurrent workers
  ```
  Apply the same to the `Retry-After` path only as an added spread (`delay + random.uniform(0, 1)`), never reducing a server-mandated wait.

#### [SUGGESTION] `genai.Client` instances created per chain walk are never closed
- **Location:** line 205 (`tier_client = genai.Client(api_key=key)`)
- **Issue:** Each `_walk_tier_chain` invocation constructs one client per key tier. Each holds an `httpx` connection pool. Because a locked-in pair failure re-enters the chain, long runs can construct many clients and leak sockets/file descriptors; the previously-locked-in client is dropped without `close()`.
- **Suggestion:** Cache clients per API key on the instance:
  ```python
  def _client_for(self, key: str) -> genai.Client:
      with self._resolve_lock:
          if key not in self._clients:
              self._clients[key] = genai.Client(api_key=key)
          return self._clients[key]
  ```

#### [SUGGESTION] `Retry-After` is honoured for OpenRouter only
- **Location:** lines 361–386 vs. lines 291–301
- **Issue:** Gemini 429 responses carry retry hints too (`RetryInfo` / `Retry-After`), but the Gemini path re-raises 429 immediately and the 503 path uses pure exponential back-off. The README now claims `Retry-After` support without scoping it to OpenRouter for readers skimming.
- **Suggestion:** Either extract the delay computation into a shared `_next_delay(attempt, retry_after_header)` helper used by both paths, or leave as-is and note the OpenRouter-only scope in the `_try_model` docstring.

#### [SUGGESTION] `float(int(value))` is a lossy parse for delta-seconds
- **Location:** line 47
- **Issue:** `int("1.5")` raises, so a fractional delta-seconds value silently falls through to the HTTP-date branch and then to `None`/exponential back-off. `int()` also accepts PEP 515 underscores (`int("1_2") == 12`) and a leading `+`, which are not valid header syntax.
- **Suggestion:**
  ```python
  if re.fullmatch(r"\d+", value):
      return float(value)
  ```

### src/audiobooks/research_papers/wiki_engine/ingestion.py

#### [CRITICAL] A classification validation failure now discards every concept in the section
- **Location:** lines 429–436 (`_SectionClassification.model_validate({k: v for k, v in data.items() if k != "concepts"})`)
- **Issue:** `_SectionClassification` is declared with `ConfigDict(extra="forbid")` and three required fields with no defaults (`category`, `title`, `paper_urls`). The combined response is validated by stripping only the `concepts` key and passing the remainder. Therefore **any** extra key the model volunteers (`"summary"`, `"reasoning"`, `"sources"`, …) or any missing required key (`paper_urls` omitted because the section has no URLs) raises `ValidationError` — and the handler returns `(default_section, [])`, throwing away a `concepts` array that parsed perfectly well. This is a strict regression: on the legacy `combined_analysis=False` path a classification failure only downgraded the category to `Other`, while `_extract_concepts` still ran and returned its concepts.
  The exposure is not theoretical: `GeminiClientWithFallback.generate()` **ignores `response_format` on all Gemini tiers** (documented at gemini_client.py lines 100–104), so whenever the wiki engine is constructed with `api_key` but no OpenRouter credentials, the strict JSON schema is never enforced and extra/missing keys are the normal case. `combined_analysis=True` is the default, so this is the default code path.
- **Failure scenario:** Gemini-backed wiki ingestion of a 6-section transcript where the model adds a `"summary"` field → 6 × `logger.warning("Section analysis failed schema validation")`, 0 concept pages created, index rebuilt and auto-committed as a successful ingest.
- **Suggestion:** Validate only the fields the contract owns, and never let a classification miss destroy concepts:
  ```python
  raw_classification = {k: data.get(k) for k in ("category", "title", "paper_urls")}
  raw_classification["paper_urls"] = raw_classification.get("paper_urls") or []
  try:
      classification = _SectionClassification.model_validate(raw_classification)
      section = ClassifiedSection(
          text=text,
          category=classification.category or "Other",
          title=classification.title,
          paper_urls=classification.paper_urls,
      )
  except ValidationError as e:
      logger.warning("Section classification invalid, defaulting: %s", e)
      section = default_section          # keep going — concepts below are still parsed
  ```
  (Everything after this point already tolerates a defaulted `section`.)

#### [WARNING] Total analysis failure is reported as a successful ingest
- **Location:** lines 397–408 (`_analyze_section_safe`), 289–296, 299–309
- **Issue:** `except Exception` converts every failure into `(Unclassified section, [])` with only a `logger.warning`. `ingest_transcript` has no notion of how many sections failed: it returns `concepts_created: []`, rebuilds `index.md`, and — when `auto_commit=True` — commits `wiki: ingest transcript <date>` as if the run succeeded. An operator watching commit history or the returned dict cannot distinguish "this transcript had no extractable concepts" from "the LLM was down for the entire run". Because the caller is a headless GitHub Actions job, this failure is silent.
- **Suggestion:** Count failures and surface them; skip the commit when nothing succeeded:
  ```python
  def _analyze_section_safe(self, index, text):
      try:
          return self._analyze_section(text)
      except Exception as e:
          logger.warning("Section %d analysis raised; skipping: %s", index, e)
          self._failed_sections += 1     # reset at the top of ingest_transcript
          return (ClassifiedSection(text=text, category="Other", title="Unclassified"), [])
  ```
  ```python
  result["sections_total"] = len(sections)
  result["sections_failed"] = self._failed_sections
  if self._failed_sections == len(sections) and sections:
      logger.error("All %d sections failed analysis; skipping auto-commit.", len(sections))
      self.auto_commit = False   # or: return result before the commit step
  ```
  Note `self._failed_sections` is mutated from pool threads — use `itertools.count`/a lock, or have `_analyze_section_safe` return a failure flag in the tuple instead.

#### [SUGGESTION] Per-request `httpx.post` prevents connection reuse under the new parallelism
- **Location:** gemini_client.py line 356 (`httpx.post(...)`), exercised concurrently from `_analyze_sections`
- **Issue:** The module-level `httpx.post` builds and tears down a fresh client (and TLS handshake) per call. With 4 workers × N sections × up to 4 retries, this adds a full handshake to every attempt.
- **Suggestion:** Hold one `httpx.Client(timeout=120)` on the instance (it is thread-safe) and reuse it for all OpenRouter calls.

- **Suggestion:** Construct it lazily in the `else` branch of `ingest_transcript`, or keep it but note in the docstring that it exists only for `combined_analysis=False`.

### src/audiobooks/reauth_gmail.py

#### [WARNING] The existing token is deleted before the OAuth flow, so a failed flow leaves no credentials at all
- **Location:** lines 60–63
- **Issue:** `os.remove(token_file)` runs unconditionally before `flow.run_local_server(port=0)`. If the flow fails — no browser on the host, the user closes the consent window, the loopback port is blocked, `credentials.json` is for the wrong client — the exception propagates out of `reauth()` and the previously working `token.json` is already gone. The script's own docstring says it is for recovering *from* a broken token; running it on a headless box turns a possibly-still-valid token into no token.
- **Suggestion:** Write to a temp path and swap only on success:
  ```python
  backup = None
  if os.path.exists(token_file):
      backup = token_file + ".bak"
      os.replace(token_file, backup)
  try:
      flow = InstalledAppFlow.from_client_secrets_file(credentials_file, SCOPES)
      creds = flow.run_local_server(port=0)
  except Exception:
      if backup:
          os.replace(backup, token_file)   # restore the previous token
      raise
  ```

#### [WARNING] `token.json` is written with default permissions
- **Location:** lines 67–68
- **Issue:** The file holds a long-lived Google refresh token for `gmail.modify` + `gmail.send`. `open(token_file, "w")` uses the process umask — `0644` on Linux/CI runners, i.e. readable by every local account. This is the same class of issue as committing a credential to a world-readable path.
- **Suggestion:**
  ```python
  fd = os.open(token_file, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)
  with os.fdopen(fd, "w") as fh:
      fh.write(creds.to_json())
  ```

#### [SUGGESTION] `--print-token` writes a refresh token to stdout with no warning
- **Location:** lines 84–91
- **Issue:** The pretty-printed JSON includes `refresh_token` and `client_secret`. If anyone runs this inside CI or with output redirected/teed, the secret lands in a log file or scrollback that is not treated as sensitive.
- **Suggestion:** Emit a one-line caution before printing (`logger.warning("Printing live credentials — do not run this with output captured or logged.")`), and consider redacting `client_secret` from the printed blob since only `GOOGLE_TOKEN_JSON` is needed.

#### [SUGGESTION] Emoji in a log record can trip Windows console encoding
- **Location:** line 74 (`"✅ Authentication successful..."`)
- **Issue:** On a `cp1252` Windows console (the documented dev environment for this repo) `logging.StreamHandler` raises `UnicodeEncodeError` internally and prints a `--- Logging error ---` block instead of the success message. The script still exits 0, so the operator sees a traceback-shaped output on the happy path.
- **Suggestion:** Drop the emoji or use an ASCII marker (`"OK: Authentication successful..."`).
