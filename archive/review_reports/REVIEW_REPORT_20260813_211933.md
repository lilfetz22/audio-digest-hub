### src/audiobooks/generate_tts_audio.py

#### [CRITICAL] A dying TTS worker aborts the whole day's audiobook — `future.result()` is unguarded
- **Location:** lines 229–243 (parallel branch of `generate_audio_from_text`)
- **Issue:** `future.result()` re-raises anything that killed the pool. If *any* worker process dies
  — OOM-killed by the kernel, segfault in espeak-ng/Kokoro, or an exception inside `_init_worker`
  (`_load_pipeline` failing on one worker while others succeed) — `concurrent.futures` raises
  `BrokenProcessPool` from the first `result()` call and every remaining future is cancelled. That
  propagates out of `generate_audio_from_text` → `generate_and_upload_audio` catches it and returns
  `[]` (`generate_audiobook.py:625-627`) → `main()` logs "TTS synthesis or upload failed" and
  `continue`s. Net effect: **no audiobook is produced or uploaded for that day at all**.

  This is a regression introduced by this change, and the failure is likely rather than theoretical.
  `daily-digest.yml:4` states the runner is "2 vCPU, 7 GB RAM — enough for Kokoro TTS without OOM"
  — i.e. sized for *one* Kokoro pipeline. `min(os.cpu_count(), 4)` = 2 on that runner, so peak
  memory roughly doubles (two torch runtimes + two copies of the Kokoro weights). `pipeline.py`
  already carries dedicated OOM/signal-detection code (`run_step`, lines 138–147), which is strong
  evidence OOM kills have happened here before. In the old sequential path a bad chunk degraded to
  0.5 s of silence and the run continued; there is now no degradation path at all, and no fallback
  to single-process synthesis.
- **Suggestion:** extract the sequential loop so it can also serve as a fallback, and catch a broken
  pool.
  ```python
  from concurrent.futures import ProcessPoolExecutor, as_completed
  from concurrent.futures.process import BrokenProcessPool


  def _synthesize_sequential(
      chunks: List[str],
      voice: str,
      speed: float,
      device: str,
      audio_chunks: List[Optional[np.ndarray]],
  ) -> int:
      """Synthesize every chunk in this process. Returns the failed-chunk count."""
      pipeline = _load_pipeline(device)
      logger.info("Warming up model...")
      _ = _synthesize_chunk(pipeline, "Warm up.", voice, speed)
      failed = 0
      with torch.no_grad():
          for i, chunk in enumerate(tqdm(chunks, desc="TTS", unit="chunk")):
              try:
                  audio_chunks[i] = _synthesize_chunk(pipeline, chunk, voice, speed)
              except Exception as exc:  # noqa: BLE001 — keep going on bad chunks
                  logger.error("Chunk failed (%s): %.80s", exc, chunk)
                  audio_chunks[i] = np.zeros(int(SAMPLE_RATE * 0.5), dtype=np.float32)
                  failed += 1
      return failed
  ```
  and in `generate_audio_from_text`:
  ```python
  if resolved_workers <= 1:
      failed = _synthesize_sequential(chunks, voice, speed, device, audio_chunks)
  else:
      logger.info("Using %d worker processes for TTS synthesis", resolved_workers)
      try:
          with ProcessPoolExecutor(
              max_workers=resolved_workers,
              initializer=_init_worker,
              initargs=(device,),
          ) as executor:
              futures = [
                  executor.submit(_worker_synthesize, i, chunk, voice, speed)
                  for i, chunk in enumerate(chunks)
              ]
              for future in tqdm(
                  as_completed(futures), total=len(futures), desc="TTS", unit="chunk"
              ):
                  index, audio, error = future.result()
                  audio_chunks[index] = audio
                  if error is not None:
                      logger.error(
                          "Chunk %d failed (%s): %.80s", index, error, chunks[index]
                      )
                      failed += 1
      except BrokenProcessPool as exc:
          logger.error(
              "TTS worker pool died (%s) — likely an OOM kill. Retrying the whole "
              "text with single-process synthesis.",
              exc,
          )
          audio_chunks[:] = [None] * len(chunks)
          failed = _synthesize_sequential(chunks, voice, speed, device, audio_chunks)
  ```
  This also removes the `np.concatenate(audio_chunks)` hazard at line 253, which would raise on any
  `None` left behind by a partially-drained pool.

#### [WARNING] Worker count is not clamped to the number of chunks — short texts get slower, not faster
- **Location:** lines 201–203
- **Issue:** `resolved_workers` ignores `len(chunks)`. `generate_audio_from_text("One short line.")`
  produces 1 chunk but still starts 4 worker processes (on a 4+ core host), each of which loads a
  full Kokoro pipeline in `_init_worker` before 3 of them sit idle. Pipeline load is the dominant
  fixed cost (see the `"Pipeline loaded in %.1fs"` timing at line 122), so this makes small inputs
  measurably slower than the sequential path — the opposite of the change's goal, and it hits the
  `generate_tts_audio.py <file>` CLI on any small digest.
- **Suggestion:**
  ```python
  resolved_workers = (
      max_workers
      if max_workers is not None
      else min(os.cpu_count() or 1, MAX_TTS_WORKERS)
  )
  # Never start more pipelines than there is work for — each one costs a full
  # model load before it does anything useful.
  resolved_workers = min(resolved_workers, len(chunks))
  ```

#### [WARNING] `--device cuda` combined with the default worker count will OOM the GPU
- **Location:** lines 201–233, plus the `--device` choices at line 312
- **Issue:** `--device` accepts `cuda`, and `initargs=(device,)` hands that straight to every
  worker, so `python generate_tts_audio.py digest.txt --device cuda` on a 4-core box creates 4
  processes that each build a separate CUDA context and load the weights into VRAM. On consumer
  GPUs that is a `CUDA out of memory` / context-creation failure in `_init_worker`, which then
  surfaces as the `BrokenProcessPool` abort described above. On Linux the pool also defaults to the
  `fork` start method, which is explicitly unsupported for CUDA-initialised state.
- **Suggestion:** force single-process for non-CPU devices unless the caller opted in explicitly,
  and use an explicit `spawn` context for the pool (safer with torch, and matches the behaviour
  already exercised on Windows/macOS):
  ```python
  import multiprocessing

  if device != "cpu" and max_workers is None:
      logger.info("device=%s: using a single process (one accelerator context).", device)
      resolved_workers = 1
  ...
      with ProcessPoolExecutor(
          max_workers=resolved_workers,
          mp_context=multiprocessing.get_context("spawn"),
          initializer=_init_worker,
          initargs=(device,),
      ) as executor:
  ```

#### [WARNING] The production path cannot tune the worker count at all
- **Location:** line 202; call site `generate_audiobook.py:624`
  (`generate_audio_from_text(text_content, mp3_filepath)`)
- **Issue:** `--workers` only exists on the standalone CLI. The real daily run is
  `pipeline.py` → `generate_audiobook.py` → `generate_audio_from_text(...)` with no `max_workers`,
  so it always takes `min(cpu_count, 4)`. Given the 7 GB runner ceiling called out in
  `daily-digest.yml:4`, the only way to dial parallelism back after an OOM is to edit and redeploy
  `MAX_TTS_WORKERS` — there is no config or environment knob, and no way to set it from the
  workflow file.
- **Suggestion:** honour an env var so CI/cron can cap it without a code change:
  ```python
  def _default_workers() -> int:
      override = os.environ.get("TTS_MAX_WORKERS")
      if override:
          try:
              return max(1, int(override))
          except ValueError:
              logger.warning("Ignoring non-integer TTS_MAX_WORKERS=%r", override)
      return min(os.cpu_count() or 1, MAX_TTS_WORKERS)


  resolved_workers = max_workers if max_workers is not None else _default_workers()
  ```
  and add `TTS_MAX_WORKERS: "2"` to the `Run pipeline` step's `env:` block in
  `.github/workflows/daily-digest.yml`.

### src/audiobooks/generate_tts_audio.py

#### [SUGGESTION] Pause markers are round-tripped through worker processes for no reason
- **Location:** lines 234–237 with `_synthesize_chunk` lines 127–128
- **Issue:** `PAUSE_MARKER` chunks require no model at all — `_synthesize_chunk` just returns
  `np.zeros(SAMPLE_RATE * 10)`. Sending them to a worker pickles ~960 KB of zeros back over the
  pipe per pause. On an interrogator-heavy digest with dozens of `Q\d+:` lines that is tens of MB
  of pointless IPC.
- **Suggestion:** fill them in the parent and only submit real speech:
  ```python
  work = []
  for i, chunk in enumerate(chunks):
      if chunk == PAUSE_MARKER:
          audio_chunks[i] = np.zeros(
              int(SAMPLE_RATE * PAUSE_DURATION_SECONDS), dtype=np.float32
          )
      else:
          work.append((i, chunk))
  futures = [executor.submit(_worker_synthesize, i, c, voice, speed) for i, c in work]
  ```

#### [SUGGESTION] Cap OpenMP oversubscription, not just torch's intra-op threads
- **Location:** line 150 (`torch.set_num_threads(1)` in `_init_worker`)
- **Issue:** `set_num_threads` covers ATen intra-op parallelism, but OpenMP/OpenBLAS pools used by
  numpy and by torch's own kernels are sized from `OMP_NUM_THREADS` at library init — which, in a
  `spawn`ed child, happens during `import torch`, *before* the initializer runs. So N workers can
  still each claim every core and thrash, eroding the speedup this change is chasing.
- **Suggestion:** set it in the parent, before the pool is created, scoped to the parallel branch:
  ```python
  os.environ.setdefault("OMP_NUM_THREADS", "1")
  os.environ.setdefault("MKL_NUM_THREADS", "1")
  ```
  Measure before/after on the target host — if it does not help, drop it rather than carry it.

#### [SUGGESTION] A mostly-silent audiobook is still uploaded
- **Location:** lines 245–256
- **Issue:** `failed` is logged and then ignored. If espeak-ng is broken in the worker environment
  every chunk fails, and the code cheerfully concatenates ~0.5 s of silence per chunk, writes the
  MP3, and `generate_and_upload_audio` uploads it as the day's digest. Pre-existing, but the worker
  pool adds a new class of environment-specific mass failure.
- **Suggestion:** refuse to publish garbage:
  ```python
  if failed and failed / len(chunks) > 0.25:
      raise RuntimeError(
          f"{failed}/{len(chunks)} chunks failed to synthesize; refusing to write "
          "a mostly-silent MP3."
      )
  ```
